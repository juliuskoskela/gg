## The model to preserve

A working copy is itself a commit (`@`); jj snapshots changes automatically, normally without Git's index/staging step. Editing or rebasing rewrites commit IDs while change IDs express continuity. Descendants may be rewritten too. A change ID can be divergent and refer to more than one commit: never silently choose one. A bookmark is a movable reference, not the current branch, and local and remote bookmarks have tracking and conflict states. Conflicts can live in commits and propagate; a rebase need not pause for resolution. Workspaces share a repository but have distinct working copies, which can become stale. Operations describe repository state changes, distinct from the commit graph. Sources: [working copy and workspaces](https://docs.jj-vcs.dev/latest/working-copy/), [bookmarks](https://docs.jj-vcs.dev/latest/bookmarks/), [conflicts](https://docs.jj-vcs.dev/latest/conflicts/), [operation log](https://docs.jj-vcs.dev/latest/operation-log/), [divergence](https://docs.jj-vcs.dev/latest/guides/divergence/), [Git comparison](https://docs.jj-vcs.dev/latest/git-comparison/).

Avoid a Git-centric branch checkout, staging area, linear history, mandatory clean working tree, or interrupted-rebase wizard as the primary model. Distinguish viewing a revision from editing the working copy; distinguish selected changes from the destination and from bookmarks. Show both change and commit identity when ambiguity matters. Rewrites and conflicts must be legible, including descendants and other workspaces.

## Touch and keyboard alternative to drag

Provide a two-step **Move revisions…** command: select one revision or a contiguous range, choose a destination revision, then review source endpoints, destination and affected descendants before applying. Reuse `MoveRevisions { set: { from: oldest, to: newest }, parent_ids: [destination] }`; this is the existing revision-to-revision drag contract, not a new CLI invocation. For insertion, offer a separate **Insert between…** with explicit after/before targets using `InsertRevisions`; adding/removing merge parents is a different `AdoptRevision` operation. The graph's direct manipulation remains available. A searchable destination picker addresses distant/offscreen targets and works with touch, keyboard and assistive technology.

Enforce the same `BinaryMutator.canDrag/canDrop` and backend preconditions, not merely visual disabling: reject an empty or invalid range and a target inside it; respect immutable source and insertion child unless explicitly overridden; validate stale or divergent identities and cycles in the worker. Show the affected scope and that children/descendants can be rewritten and conflicts created. `MoveRevisions` is a selected-range operation with descendant handling, not an unqualified promise to move an entire subtree. Give mutation errors and refreshed status; do not claim a preflight count is exact unless computed by the backend. Destructive or consequential commands need explicit scope: abandon rewrites children, forget may abandon an empty working copy, delete bookmark can propagate on push, and push/fetch address specific remotes and refs. Preserve the existing explicit immutable override rather than quietly bypassing it.
